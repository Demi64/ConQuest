# 実装メモ（技術的な設計判断の記録）

最終更新：2026-11-10

`docs/mvp.md` の範囲を実装するときに実装側で決めたことをまとめる。仕様（mvp.md・spec-draft.md）と違う動きにした点は「仕様からの変更・補足」に書く。

## 1. 構成

```
src/
  index.ts            入口。全体を OAuthProvider で包み、/mcp だけ接続用トークン必須にする。Cron もここ
  core/               このツール固有のロジック（接続方法に依存しない）
    store.ts          書き込みの土台 Tx。全ての書き込みを変更履歴に記録する
    ops.ts            書き込みの操作（MCP・画面・提案の承認のどこから来てもここを通る）
    schemas.ts        操作の入力の形（zod）。MCPのツール定義と画面のAPIで共用
    views.ts          読み出し（概要・クエスト詳細・検索・履歴）。導出項目の計算
    daily.ts          デイリーの生成・締め・繰り越し
    undo.ts           取り消し
    context.ts        「誰が・いつ・設定」と、AIの実行のまとめ方
  mcp/                MCPサーバー（16操作）とAI向けの説明文
  web/                画面用API、ログイン、MCPの接続許可ページ
  ai/                 AIの起動（差し替え可能）と、30秒まとめる待ち合わせ
  calendar/           Googleカレンダーの読み込み
  shared/             サーバーと画面で共有する型・文言
web/                  画面（Preact）。esbuild で public/assets にまとめる
migrations/           データベース定義
prompts/              スケジュール済みタスクに渡すプロンプト
scripts/smoke.mjs     動作確認（画面のAPIとMCPをひと通り呼ぶ）
```

| 役割 | 採用 | 理由 |
|---|---|---|
| MCPサーバー | Cloudflare の `agents`（`createMcpHandler`）＋ `@modelcontextprotocol/server` | 公式の実装例どおり。状態を持たない方式（Durable Object 不要） |
| MCPの認証 | `@cloudflare/workers-oauth-provider` | 公式ライブラリ。クライアント登録・トークン発行・検証を任せる。保存先はKV |
| 画面用API | Hono | ルーティングとHTMLのエスケープ |
| 画面 | Preact＋esbuild | 小さく、ビルドが速い。画面数が少ないのでフレームワークは使わない |
| テスト | `scripts/smoke.mjs`（手元のサーバーに対する通し確認） | Workers用のテスト基盤（vitest-pool-workers）が現時点の依存関係で入らなかったため。入るようになったら単体テストを足す |

## 2. データ

- 定義は `migrations/0001_init.sql`。IDは全てUUID。時刻はUTCのISO文字列、日付は設定のタイムゾーンでの `YYYY-MM-DD`。期限は日付または `YYYY-MM-DDTHH:MM`。
- ユーザー・ゾーン・HUDレイアウト・端末の表は作っていない（mvp.md 3章）。利用者は1人。
- 設定は `settings` 表（key/value）。利用者の設定は `user_settings` に1つのJSONで持つ。
- 「誰が」（ai／human／system）は接続元で決める：MCP経由＝ai、画面のAPI＝human、Cronと定型処理＝system。

### 変更履歴と取り消し
- 書き込みは必ず `Tx`（core/store.ts）を通す。1回の操作が `operations` の1行、その中の行ごとの変更が `changes`（変更前・変更後のJSON）。D1 の batch で、データの書き込みと履歴の記録を「全部成功か全部失敗」にしている。
- 取り消しの単位は「操作1件」または「AIの実行1回」。取り消しも1件の操作として記録するので、取り消しの取り消しができる。
- 追加の取り消しは、行を消さず `deleted_at` を立てて見えなくする（「削除は破棄扱い」を守るため）。紐づけの表（予定の紐づけ・前提クエスト）だけは行を消す。
- 変更の取り消しは項目ごと。取り消したい変更のあとに同じ項目が別の値に変わっていたら、その項目は戻さず件数を返す。
- 取り消せない操作：デイリーの切り替え、完全削除、設定の変更。
- 完全削除（人が画面から、破棄済みのクエストにだけ）は、タスク・ジャーナル・提案・紐づけと、履歴に残っている中身（changes）も消す。「完全に削除した」という1行だけ残る。

### AIの実行（runs）
- MCPサーバーは状態を持たない方式なので、会話やセッションの単位が分からない。そこで**最後のMCP呼び出しから10分以内は同じ実行**としてまとめる。
- アプリからAIを起動した直後（5分以内）に始まった呼び出しは、新しい実行にして「アプリからの入力」と記録する。それ以外は「Claudeとの会話」。

### 外部カレンダーの写し
- `calendar_events` は写しなので変更履歴の対象外。紐づけ（`event_links`）は履歴の対象。
- 取り込みは15分ごと。範囲は昨日〜90日先。Googleカレンダーの画面で表示にしているカレンダーが対象。
- 時刻つきの予定はUTCにそろえて保存し、返すときに設定のタイムゾーンの日付・時刻に直す（AIにも画面にも同じ形で渡す）。
- Googleの更新用トークンは `ENCRYPTION_KEY`（secret）で暗号化して `settings` に保存する。

## 3. 定型処理

- Cron は15分ごと。「日付が変わっていたらデイリーを切り替える」「カレンダーを取り込む」の2つ。
- デイリーの切り替えは、Cron が遅れても困らないよう、画面やMCPの読み書きのたびにも確認する（`ensureDay`）。同時に2回走らないよう、先に「今日の分は処理した」印を取る。
- 切り替えの中身：前日までのデイリーを締める（状態を完了に）→ 未完了タスクを今日のデイリーの先頭へ移して繰り越し回数＋1 → 繰り返しの定義から今日の分を生成。
- 同じ定義から出たタスクが繰り越されて残っているときは、今日の分を重ねて出さない（「ゴミ出し」が2つ並ばないように）。
- 日付を指定して予約し直したタスク（`move_tasks` の `to_daily_date`）は、繰り越し回数を0に戻す。

## 4. AIの起動

- `ai/launcher.ts` の `AiLauncher` を差し替えれば起動方法を替えられる。今はスケジュール済みタスクのAPIトリガー。
- 起動先のURL（Fire URL）とトークンは secret（`ROUTINE_FIRE_URL`・`ROUTINE_TOKEN`）。未設定なら起動を予約しない（入力は保存され、Claudeとの会話からも整理できる）。
- 待ち合わせは Durable Object（`AiQueue`）のアラーム。きっかけのたびに30秒後へ延ばす。上限（1時間30回）の手前、25回で止めて次の空きまで待つ。混雑・一時的な失敗は5分おきに3回までやり直す。
- 「整理中」の印：起動待ち、起動してからAIが動き出すまで（最長5分）、AIの最後の呼び出しから1分間。

## 5. 認証

- 利用者は1人。画面も、MCPの接続許可も、パスワード（secret `OWNER_PASSWORD`）で本人を確かめる。失敗が15分に10回を超えると受け付けない。
- 画面のログインはクッキー（90日）。データベースにはトークンのハッシュだけ置く。
- MCPの接続先のアドレスは設定ファイルに書かず、届いたリクエストのアドレスから組み立てる（デプロイ先を変えても設定不要、アドレスをリポジトリに入れない）。

## 6. 仕様からの変更・補足

1. **入力を処理済みにする方法**：ドラフト6章は「作成・追加が成功した時点で処理済み」。実際には完了の報告など、作成・追加を伴わない入力もあるので、**全ての書き込み操作に `source_input_ids` を付けられる**ようにした。
2. **変更が要らない入力**：処理済みにする手段がないと残り続けるため、`get_overview` に `acknowledge_input_ids` を足した（操作の数は16のまま）。履歴には残る。
3. **報告待ちの条件**：ドラフトは「未完了タスクが0件」。タスクを1つも登録していないクエストまで報告待ちになるので、**タスクが1件以上あり、未完了が0件**のときにした。
4. **完了・破棄から戻す操作**：AIは完了済みのクエストを動かせない。破棄から戻すのも画面からだけ（「受注中に戻す」）。
5. **状態と追跡**：受注したら追跡オン、保留・Quest Board・破棄・完了にしたら追跡オフにする。
6. **提案の中身にできる操作**：`set_quest_status`・`update_quest`・`set_task_status`・`update_task`・`move_tasks`・`add_tasks`・`append_journal`・`set_recurring`。
7. **提案の期限切れ**：対象のタスクが完了・やめたになったとき、対象のクエストの状態が変わったときに期限切れにする。承認したが実行できなかった場合も期限切れ。
8. **同じ提案の判定**：対象と中身（操作と引数）が同じもの。却下から30日は出せない。
9. **人の手での編集（MVPの画面）**：タスクの追加・完了・やめた、ジャーナルの追記、状態の変更、追跡の切り替え、予定の紐づけ、繰り返しの有効／停止。項目の細かい編集（期限の変更など）は今は AI 経由（Claudeに頼む）。
10. **Quest Board の用語**：コード上の状態名は `board`。

## 7. 後回しにしたこと（MVPの外）

- オフライン対応、プッシュ通知、複数ユーザー、ゾーン・端末、HUDの自由配置、昇格・降格（`convert`）
- 全データの書き出し（当面は `wrangler d1 export` で代用できる）
- クエスト・タスクの横の提案の印は、件数の表示だけ（その場で中身を開く表示はクエスト詳細で行う）
